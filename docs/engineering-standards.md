# DBJavaGenix 项目工程规范

本文件是项目协作、提交、合并、测试和发布的唯一规范入口。规则适用于维护者和贡献者；自动化检查逐步落实本文件中的门禁。

## 1. 工作流：Issue -> Branch -> Commit -> PR -> Merge

除紧急安全修复外，所有变更按以下顺序进行：

1. 先创建或补充 Issue，说明背景、目标、非目标、验收标准和风险。
2. 从 `main` 创建短生命周期分支：`feat/<issue>-<name>`、`fix/<issue>-<name>`、`docs/<issue>-<name>`、`test/<issue>-<name>` 或 `chore/<issue>-<name>`。
3. 以小步提交实现一个可验证的行为；一个提交应能独立理解、检查和回滚。
4. 提交 Pull Request，关联 Issue（使用 `Closes #123` 或 `Refs #123`），等待 CI 通过和代码审查。
5. 只通过 PR 合并到 `main`。合并前必须解决阻塞性评论，并确认测试、文档和兼容性影响。

紧急安全修复可以先提交最小修复，再在 24 小时内补建 Issue、测试和复盘记录。

## 2. 标题与编码规范

Issue、PR 和提交使用同一个标题语法：先写 Gitmoji，再写
[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 类型和范围。

### 中文优先

Issue 和 PR 的标题、正文描述默认优先使用中文，确保背景、验收标准、实验结果和风险对中文协作者清晰可读。Gitmoji、Conventional Commits 类型、代码标识、命令、API 名称、错误信息和数据库专有名词保留原文；涉及跨团队协作时可以补充英文摘要。

```text
:gitmoji: type(scope): 清晰、可验证的简短动作
```

`scope` 是必填的、小写 ASCII 模块名，可使用 `-`、`_`、`.` 或 `/` 连接，应该指向
实际责任边界，例如 `mcp`、`metadata`、`generator`、`dialect`、`cli`、`ci`、`docs` 或
`governance`。不要使用 `misc`、`update`、`all` 等没有信息量的 scope；跨模块变更用最主要的
公共边界，并在正文列出其余影响模块。

Gitmoji 使用短代码，保证终端、GitHub 和自动化工具中的显示一致。常用映射如下：

| Gitmoji | 类型 | 用途 |
| --- | --- | --- |
| `:sparkles:` | `feat` | 新增用户可见能力 |
| `:bug:` | `fix` | 修复错误行为 |
| `:test_tube:` | `test` | 新增或调整测试 |
| `:books:` | `docs` | 文档、规范或 ADR |
| `:recycle:` | `refactor` | 不改变外部行为的重构 |
| `:zap:` | `perf` | 性能改进 |
| `:construction_worker:` | `ci` / `build` | CI、构建或依赖 |
| `:lock:` | `security` | 安全修复或加固 |
| `:wrench:` | `chore` | 其他维护工作 |
| `:rocket:` | `release` | 发布和版本变更 |

类型必须与 Gitmoji 映射一致。`feat` 表示新增用户可见能力，`fix` 表示修复可复现的错误，
`refactor` 不得宣称外部行为变化，`perf` 必须有可重放的性能证据；只有修改 CI/构建时才使用
`ci` / `build`。

所有标题和正文均为 UTF-8。提交前必须在终端和 GitHub 预览中检查中文；连续 `??`、乱码替代
符或原生 Unicode Emoji 前缀都视为损坏，应先修复编码再提交。Gitmoji 一律使用短代码，例如
`:bug:`，不能使用 `🐛`。标题首行最多 72 个字符、不以句号结尾，并以描述动作的动词开头。
Issue 可以先描述问题，但同样必须使用标题语法，不能使用 `config`、`init`、`.gitignore`、
`Initial commit` 等无上下文文本。

提交额外要求：

- 每次提交只解决一个主题；不要把格式化、重命名和功能混在同一提交中。
- 提交前运行与改动相关的最小测试集；跨模块变更运行完整单元测试。
- 不提交密钥、数据库密码、个人配置、生成目录、覆盖率产物或构建缓存。
- 推送前修正本分支中错误的未合并提交；已经合并的历史不强制重写，以后续、单独的维护提交
  覆盖其文件元数据。

CI 校验 PR 标题、PR 内全部提交标题和 PR 正文的必备章节、顺序和非空内容。独立的
`Repository metadata` workflow 会在 Issue 创建、编辑或重新打开时校验标题和对应正文模板；
它不触发数据库、Docker 或 Java 构建。两个门禁都会拒绝连续 `??`、Unicode 替代字符、控制
字符和将换行错误写成字面量转义的正文。它们只检查结构和编码信号，不会把测试或性能结论当成
已经证明的事实；审查者仍须检查命令、输出和声明是否匹配。

## 3. Issue 要求

所有新 Issue 的标题遵从第 2 节。Bug 和功能表单分别提供固定字段；手工创建的 Issue 也必须
保留同等信息。

Bug Issue 正文按以下顺序填写：

1. `版本与环境`：受影响提交、运行时、数据库和安装方式，不能包含凭据。
2. `问题与预期行为`：实际行为、预期行为及用户/数据影响。
3. `最小复现`：可执行步骤、脱敏输入和错误输出。
4. `验收标准`：能证明修复的可勾选、可测试条件。
5. `非目标、风险与安全`：明确不改什么、兼容性/回滚风险；安全问题转到 `SECURITY.md` 的私下
   流程。

功能或架构 Issue 正文按以下顺序填写：

1. `问题与用户价值`：受益者、现状和不处理的成本。
2. `建议方案与替代方案`：拟修改的模块、被拒绝或待比较的方案。
3. `验收标准`：功能、错误语义、测试和文档的可验证条件。
4. `架构、兼容性与测试计划`：公共 API、数据格式、迁移、真实数据库或基准的证据计划。
5. `非目标与风险`：避免将未来优化、未测量性能收益或不相关重构混入本 Issue。

Issue 在关闭前应由关联 PR 的 `Closes #<number>` 自动关闭；仅作研究、路线图或尚未完成的任务用
`Refs #<number>`，并在评论中说明状态而不是提前关闭。

Issue 创建、编辑或重新打开后会触发轻量元数据门禁。失败时先修复标题、补齐相应固定章节，并将
实际换行替换掉字面量 `\\r\\n`/`\\n`；不要通过删除中文、把内容改成 `?` 或关闭 Issue 绕过校验。
Issue 表单会生成三级标题，手工 Markdown 使用二级标题，两种格式都受同一章节合同约束。

## 4. PR 要求

PR 标题必须与提交使用同一套格式。PR 正文必须按下列固定标题填写，CI 会检查这些章节的精确名称、
顺序、非空内容，以及 `Closes #<number>` 或 `Refs #<number>` 关联：

1. `关联 Issue`：关闭或引用的编号及其验收目标。
2. `背景（Situation）`：现有行为、受影响用户和问题根因。
3. `任务（Task）`：本 PR 的完成条件和明确边界。
4. `行动（Action）`：按模块说明实现、测试和文档改动；单列没有做什么。
5. `验证（Verification）`：逐条列出实际执行的命令、环境和结果。未执行的检查必须明确说明原因，
   不能写成“通过”。
6. `实验与证据（Evidence）`：输入、方法、原始输出位置和结论；没有实验时写“无”，不得以理论
   推导声称性能提升。
7. `兼容性、风险与回滚`：公共 API、数据/配置迁移、已知限制、回滚提交或步骤、后续 Issue。

PR 中的复选框只用于审查跟踪，不能代替命令输出。涉及公共工具、数据库方言、SQL 或安全边界时，
必须描述错误语义、参数化/脱敏策略和至少一个反例或回归测试。涉及架构决策时，必须链接或新增
ADR；只改实现细节时说明为何不需要 ADR。

合并门槛：

- CI 必须通过；失败的检查只能通过修复或有记录的维护者豁免处理。
- 至少一次维护者审查；涉及安全、数据访问或公共 API 时需要额外审查。
- 新功能必须有测试；缺陷修复必须有能复现并防止回归的测试。
- 行为变化必须同步更新 README、API 文档、ADR 或迁移说明。
- 优先使用 Squash merge，合并后的提交仍应保留清晰的 Conventional Commit 标题。

## 5. PR 回帖与审查记录

PR 回帖记录的是可追溯的工程事实，不是固定数量的进度播报。至少在实现完成和验证完成两个
里程碑各发一条有实质内容的评论；出现设计取舍、真实环境实验、CI 失败/豁免或风险变化时，再
补充对应评论。每条评论使用以下粒度：

```markdown
## <阶段或结论>（YYYY-MM-DD）

### 当前结论
<已证明的结论，以及尚未证明的部分>

### 变更与设计取舍
- 提交：`<short-sha>`
- <涉及模块、替代方案和选择理由>

### 验证与证据
- `<命令>`：<实际输出或结果>
- <环境、输入、原始日志或报告位置>

### 兼容性与下一步
- <风险、未运行检查、回滚方式或待办>
```

评论只报告已执行的工作。测试数量、性能数字、线上状态和人工验证必须能追溯到命令、环境、
输入或受控日志；不能把一次偶然成功、未运行的 CI、推测的架构收益或无关失败写成通过。引用
外部示例时吸收其“结论、证据、边界”粒度，不复制设备标识、密钥、个人数据或无关长日志。

## 6. 测试和质量门禁

本地最小检查：

```bash
PYTHONPATH=src python -m pytest tests/unit/ -q
python -m ruff check src/ tests/
python -m ruff format --check src/ tests/
```

涉及数据库适配器或 SQL 行为时，额外运行：

```bash
PYTHONPATH=src python -m pytest tests/integration/ -q
```

测试应优先使用确定性 fixture；真实数据库测试通过 `DBJAVAGENIX_TEST_*` 环境变量显式启用。测试不得依赖个人机器上的凭据或服务。

## 7. 架构变更

- 先写 ADR，再实现跨模块架构决策；ADR 说明上下文、候选方案、决策、后果和迁移计划。
- 保持 Skills（流程编排）、MCP tools（能力接口）、Apps（展示层）边界，不让展示层直接访问数据库。
- 新增公共工具必须定义输入输出模型、错误语义、日志/指标和测试策略。
- 依赖升级必须说明安全、兼容性和运行时影响；锁定或记录可复现的版本范围。

## 8. 版本和发布

版本遵循 [Semantic Versioning 2.0.0](https://semver.org/)；变更记录遵循 [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)。发布前确认：

- CI、单元测试、必要的集成测试和模板渲染检查通过；
- README、迁移说明和公开 API 文档已更新；
- 依赖和安全扫描无未处理的高危问题；
- 发布说明包含用户影响、升级步骤、已知限制和验证结果。

## 9. 安全

不要在 Issue、PR、日志或测试报告中粘贴令牌、密码、连接串或完整数据库输出。安全漏洞请按 [`SECURITY.md`](../SECURITY.md) 私下报告。
