# v0.1 时期 向量库做 tool search 尝试 - 复盘

> 同 [v0.1-langchain-orchestrator] 一起,记录 2024 年的另一个失败尝试。

## 起因

v0.1 一共暴露了 ~15 个工具(db_query_*, db_codegen_*, db_table_describe 等)。
当时的想法:**"用户用自然语言提需求,Claude 不一定能在工具名里命中,需要语义搜索"**。

例如用户说"从订单表生成代码",代码里没有 `order` 这个词,工具叫 `db_codegen_generate`。期望 embedding 能桥接这个 gap。

## 实际做了什么 (2024-12)

引入依赖:
```
sentence-transformers==2.2.2  (带 torch + transformers,~ 500MB)
hnswlib==0.7.0
```

加了一个启动钩子,把每个工具的 `description` 喂给 `all-MiniLM-L6-v2`,生成 384 维向量,存到 hnswlib index。

加了一个 `tool_semantic_search(query)` 函数,query 走同样模型,top-3 返回。

## 测量结果(15 工具规模)

设计了 30 个测试 query(自然语言提问 ↔ 应命中工具):

| 检索方式 | top-1 命中率 | 平均延迟 |
|---------|------------|---------|
| 关键词(name+description 子串匹配 +分数) | 86.7% | 0.4 ms |
| Embedding (hnswlib top-1) | 83.3% | 18 ms |
| Embedding + 关键词 reranker | 90.0% | 22 ms |

Embedding 比纯关键词 **慢 45 倍但准确率反而低**。

### 为什么 embedding 输了?

1. 工具名本来就 self-describing(`db_codegen_generate`,`db_table_describe`),关键词匹配命中率高
2. embedding 对短文本(8-20 字描述)区分度不够,把 `query_tables` 和 `query_columns` 混了
3. 训练数据偏 NL 任务,我们的 `Generate Java entity from table` 在 embedding 空间里和 `Build SQL from natural language` 距离很近

### 成本副作用

- 启动多 1.2 秒(加载 MiniLM 模型 + 建 hnswlib index)
- 内存 +50MB
- Docker 镜像 +500MB (sentence-transformers + torch)
- 客户端冷启动可感知

## 决策

2024-12 中放弃,改用 **基于 tag + name + description 子串的加权评分**:
- exact name match: +10
- tag 命中: +3
- name substring: +2
- description substring: +1

这个版本至今(2025-09)还在用,15 工具规模下精度 90%+。

## 学到的

1. **工具数小 + 命名规则 = keyword 胜**:embedding 收益要在 100+ 工具且名称模糊时才显现
2. **延迟也是成本**:18ms 看起来小,但对 progressive discovery(每会话首调用都要查)是直接体感
3. **依赖的体积是成本**:500MB 安装包对 Docker / uvx 部署是负担
4. **试了才知道 — 但试之前的预期管理是关键**:我以为 embedding 必胜,实测才发现规模不够

## 这个失败有什么用?

写在 ADR-005 "不引入向量数据库" 的背后,就是这次复盘。
不是 "我们没想过",而是 "我们试过,数据说不要"。

后续如果工具数膨胀到 50+,可以重启评估。但当前 (v0.2 设计中 29 工具) 仍然在 keyword 占优区间。
