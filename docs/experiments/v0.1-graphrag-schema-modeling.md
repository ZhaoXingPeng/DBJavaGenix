# v0.1 时期 GraphRAG schema modeling 尝试 - 复盘

> 系列第三篇,2024 末试过的最"花哨"的方向。

## 当时的想法

"代码生成的本质是理解 schema 中的业务实体和关系" → 看起来像图问题。
那时刚出 GraphRAG (微软 2024-05 公开),很 hot。

把每张表当节点,每个 FK 当边,跑 GraphRAG 那一套(社区检测 → 摘要 → 全局回答)。
期望:**让 LLM 通过图理解"这是 RBAC 三表"**,而不是逐表分析。

## 实际做了什么 (2024-12 ~ 2025-01)

技术栈:
```
networkx==3.2
graphrag==0.1.0  (微软官方库,还在 alpha)
```

实现:
1. 拉 information_schema 全部表 + FK
2. 构建无向图 G(节点=表,边=FK)
3. 用 Louvain 跑社区检测,得到簇 (cluster)
4. 每个簇生成 "summary"(让 LLM 描述这些表的业务意图)
5. 拼到全局 prompt 里

### 实测样本

在一个有 60 张表的真实库上跑:
- 社区检测找到 8 个簇(订单簇 12 表 / 用户簇 8 表 / 字典簇 5 表 / 日志簇 4 表 / ...)
- 每簇 summary ~150 字
- 全局 prompt = system + 8 个簇 summary + 用户 query = ~4500 input tokens

### 结果

**和直接喂 schema 列表(2200 tokens)比,效果差不多**:
- 都能正确识别 RBAC 三表(sys_user / sys_role / sys_user_role)
- 都能正确推断业务命名
- GraphRAG 路径多了一次预处理(Louvain + summarize),延迟 +8 秒
- Token 翻倍但回答质量没有显著提升

### 为什么没用?

1. **schema 已经是结构化数据**:information_schema 本来就告诉你 "这是 user 表,这是 user_role 表",不需要 LLM 二次理解
2. **FK 关系就是事实,不需要推理**:`sys_user_role` 有两条 FK 指向 sys_user 和 sys_role,这是 100% 确定的事实,GraphRAG 那套"通过图推理"是在做已经显式的事
3. **GraphRAG 适合非结构化 → 结构化**:它的杀手场景是从大量文档中抽取实体关系。我们的输入已经是结构化的。

## 但是 — 这次"失败"实际有价值

副产品发现:
- **网络图算法对 schema 是有意义的**:Tarjan SCC 可以检测 FK 循环依赖(典型 anti-pattern),Kahn 拓扑排序可以给出 DDL 顺序 / Service 注入顺序,Union-Find 可以做"业务簇"识别
- 这些**算法本身**有价值,只是不需要包装成 "RAG"

所以这次的产出是:
- 知道 GraphRAG 不适合
- 但记下了 schema graph 算法的方向 — 等 v0.2 时把 Tarjan / Kahn / Union-Find 直接实现成工具(`schema_topo` / `schema_cluster` / `schema_cycle_check`),不要套 GraphRAG 框架

## 学到的

1. **"看起来像图问题" 不等于 "应该用 GraphRAG"**:结构化数据用图算法,非结构化数据用 GraphRAG。区别在 input 是否需要从原始文本抽取
2. **算法是底层工具,不是叙事核心**:写代码生成器讲"我们有 GraphRAG" 是错位,讲"我们有拓扑排序保证 DDL 顺序"才对位
3. **失败的探索常常埋下后续的种子**:这次没用 GraphRAG,但搞清楚了 schema 算法的边界

## 后续 (写于 2025-09)

打算在 v0.2 后期加入这三个算法:
- `schema_topo`(Kahn / Tarjan):拓扑排序生成 DDL 顺序
- `schema_cluster`(Union-Find on FK):业务簇识别
- `schema_cycle_check`(DFS):FK 循环检测

放在 src/dbjavagenix/algorithms/ 下,作为代码生成器的"图分析"底层。这部分不是 RAG,不是 LLM,是纯算法。
